# Пилот, KPI и критерии приёмки

Документ закрывает этапы 5 «Пилот», 6 «Промышленный запуск» и 7 «Оценка
результатов» ТЗ: как считаются ключевые показатели, как устроен пилот и какие
риски остаются.

---

## 1. KPI (ТЗ, п. 1)

Целевые значения `[X]`, `[Y]`, `[Z]` фиксируются с заказчиком **до** старта
пилота. Ниже — способ замера и базовые значения, которые уже можно посчитать.

| KPI | Формула | Источник данных | Baseline (сейчас) |
|---|---|---|---|
| **X** — рост конверсии предложений в сделки | показы, перешедшие в сделки / все показы | журнал показов рекомендаций + `Сделки` | офлайн-прокси: **HR@5 = 0.262** — доля сделок, где реально купленная монета была в топ-5 рекомендаций |
| **Y** — сокращение срока «закупка → продажа» | среднее (`ДАТА ПРОДАШИ` − `ДАТА ПОКУПКИ`) в днях | `Сделки` | **не считается**: `ДАТА ПОКУПКИ` не заполнена ни разу (FAIL в аудите) |
| **Z** — доля продаж по рекомендациям | сделки из топ-K / все сделки за период | журнал показов + `Сделки` | офлайн-прокси: **покрытие фильтров = 73.8%** — доля сделок, которые система могла бы рекомендовать |

### Как считать X и Z на пилоте

1. При каждом контакте с клиентом фиксируется показ: `дата, ID клиента, ID монеты, ранг в выдаче`.
2. Сделка связывается с показом по паре (`ID клиента`, `ID монеты`).
3. `X = показы_с_сделкой / все_показы`; `Z = сделки_с_показом / все_сделки`.
4. Сравнение с контрольной группой (см. п. 2) даёт **прирост**, а не абсолютное значение.

До введения журнала показов X и Z считаются только как офлайн-прокси
(`reports/metrics.csv`).

## 2. Дизайн пилота (этап 5)

| Параметр | Решение |
|---|---|
| Выборка | 2–3 клиента из 5 (рекомендуется `Шувалов` — 23 сделки, узкий профиль; `Гогер` — 6 сделок, выраженный профиль) |
| Противовес | остальные клиенты — контрольная группа, рекомендации выдаются как раньше (по усмотрению менеджера) |
| Длительность | 4–6 недель **или** минимум 20 показов на клиента (иначе X статистически не значим) |
| Выдача | топ-5 по каждому клиенту из `reports/recommendations.xlsx`, с обоснованием из колонки «Обоснование» |
| Что фиксируем | показ (дата, клиент, монета, ранг), решение (купил/отказался/отложил), причину отказа (вне бюджета / не тот стиль / уже есть / нет денег) |
| Обновление данных | пересчёт рекомендаций раз в неделю: `python -m recommender` |

**Приёмка пилота:** рост X против контроля, отсутствие отказов по причине
«уже такое есть» (проверка критерия новизны в бою) и заполненность журнала
показов ≥ 90%.

## 3. Промышленный запуск (этап 6)

1. Регулярная выгрузка Google Sheets → `data/coins.xlsx` (ручная или через
   API Google Sheets).
2. Расчёт: `python -m recommender --top-k 5` → обновляется
   `reports/recommendations.xlsx`.
3. Автопроверка качества перед расчётом: если в
   `reports/data_quality_report.csv` появился `FAIL` — расчёт останавливается,
   уведомление ответственному (иначе система тихо выдаёт неверные рекомендации).
4. Еженедельный пересчёт профилей (интересы и бюджет со временем меняются).
5. Логирование выдачи: какая монета на каком ранге была показана (запуск X/Z).

Изменения в весах и параметрах (`recommender/config.py`) — только через
согласование с РП (ТЗ, п. 4.2, требование о фиксированном наборе правил).

## 4. Критерии приёмки (ТЗ, п. 7) — статус

| Критерий | Статус | Подтверждение |
|---|---|---|
| Модель обучена и воспроизводима | ✅ выполнен | `python -m recommender` воспроизводим на любой выгрузке; параметры в `config.py`; офлайн-метрики в `reports/metrics.csv` |
| Регулярное обновление таблиц настроено и проверено | ⚠️ частично | контроль качества настроено (30 проверок, чек-лист в `docs/Требования_к_данным.md`); автоматическая синхронизация Google Sheets → репозиторий не настроена |
| Пилот подтверждает гипотезу по конверсии и сроку продажи | ⛔ не начат | требуется журнал показов и заполнение `ДАТА ПОКУПКИ` (иначе KPI Y не считается) |
| Документация передана заказчику | ✅ выполнен | `README.md`, `docs/`, ноутбук `notebooks/` |

## 5. Риски и допущения (ТЗ, п. 6) — актуализация

| Риск из ТЗ | Статус | Мера |
|---|---|---|
| Неполнота / неоднородность исторических данных | **подтверждён** | аудит нашёл 1 FAIL и 3 WARN; цена у кандидатов восстанавливается по аналогам с указанием источника оценки |
| Отсутствие данных о предпочтениях | закрыт частично | профиль строится из фактических покупок; при 1–2 сделках профиль бедный → эскалация бюджета и меньшая точность (покрытие по клиентам: `Лейбов` 1 сделка — профиль фактически не построен) |
| Устаревание каталога доступных монет | закрыт | фильтр `СТАТУС=доступна` применяется при каждой генерации; актуальность даты в отчёте (`ACT-01`) |
| *(добавлен)* незаполненная `ДАТА ПОКУПКИ` | **подтверждён** | KPI Y заблокирован до заполнения |

Допущения ТЗ приняты без изменений.

## 6. Доработки, рекомендуемые до пилота

1. **Заполнить `ДАТА ПОКУПКИ`** — иначе этап 7 не закроет показатель Y.
2. **Вносить `описание` и цену у кандидатов** — вернёт мотив в критерий профиля
   и заменит оценку цены фактической.
3. **Ввести журнал показов** — без него X и Z считаются только как прокси.
4. Уточнить целевые значения `[X]`, `[Y]`, `[Z]` — сейчас в ТЗ это плейсхолдеры.
5. Повторить анализ чувствительности на данных пилота (сейчас параметры
   подобраны на 42 сделках).
