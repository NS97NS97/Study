# Требования к данным (этап 1 ТЗ)

Документ фиксирует структуры таблиц, правила их обновления и результаты аудита
текущей выгрузки. Основа — ТЗ, п. 4; реализация контроля —
`recommender/validation.py` (30 проверок), отчёт —
`reports/data_quality_report.csv`.

---

## 1. Источники

Единая книга Google Sheets, две закладки (ТЗ, п. 4.1):

| № | Закладка | Назначение | Обновление |
|---|---|---|---|
| 1 | `Сделки` | единый список монет: статус + история сделок | при смене статуса монеты и при совершении сделки |
| 2 | `Клиенты` | сопоставление имени покупателя уникальному UUID | при появлении нового клиента |

Локальная копия для расчётов — `data/coins.xlsx` (выгрузка из Google Sheets).

---

## 2. Структура закладки «Сделки»

| Атрибут | Формат | Обязательный | Описание |
|---|---|---|---|
| `ID монеты` | uuid | да | уникальный идентификатор монеты |
| `СТАТУС` | `продана` / `доступна` / `резерв` | да | статус доступности монеты |
| `ГП2` | текст, напр. `1135А` | нет | номер по ГП2; может отсутствовать или быть заменён флагом `NEW` |
| `Княжество` | справочник | да | географическая/историческая привязка |
| `Князь` | справочник | нет | инициалы или имя князя |
| `номинал` | `денга` / `полуденга` / `пуло` | для проданных | номинал |
| `описание` | текст | для проданных | краткое описание мотива (`лицо/строчник`) |
| `R` | целое 1–7 | нет | редкость по ГП, арабскими цифрами |
| `вход` | число > 0 | для проданных | цена покупки (закупка) |
| `у кого` | текст | нет | продавец |
| `ДАТА ПОКУПКИ` | д.м.г | **для проданных** | дата закупки |
| `ДАТА ПРОДАЖИ` | д.м.г | для проданных | дата продажи |
| `продажа` | число > 0 | для проданных | цена продажи |
| `ID клиента` | uuid | для проданных | покупатель (есть в справочнике `Клиенты`) |
| `кому` | текст | для проданных | имя покупателя (для чтения человеком) |
| `маржа` | число | для проданных | `= продажа − вход` |
| `%` | доля | для проданных | `= маржа / вход` (ячейка формата «процент») |

> **Расхождение с ТЗ.** В ТЗ столбец назван «ДАТА ПРОДАШИ», в выгрузке источника —
> «ДАТА ПРОДАЖИ». Система принимает оба написания и приводит их к канону
> источника. Рекомендация — согласовать единое написание в ТЗ.

**Пустые значения** в обязательных атрибутах недопустимы; контроль — проверки
`REQ-*` и `REQS-*`.

### Справочник «Клиенты»

| Атрибут | Формат | Обязательный |
|---|---|---|
| `ID клиента` | uuid | да |
| `Клиент` | текст | да |

Все `ID клиента` из «Сделок» обязаны присутствовать в справочнике (проверка
`ID-03`); клиенты без сделок помечаются (`ID-04`).

## 3. Правила обновления (п. 4.2, требование 1)

| Событие | Действие с таблицей |
|---|---|
| Монета закуплена | новая строка: `ID монеты`, `СТАТУС=доступна`, `ГП2`, `Княжество`, `Князь`, `номинал`, `описание`, `R`, `вход`, `у кого`, `ДАТА ПОКУПКИ` |
| Монета зарезервирована | `СТАТУС=резерв` (резерв кандидатом не является, пока не вернётся в `доступна`) |
| Монета продана | `СТАТУС=продана` + заполнить `ДАТА ПРОДАЖИ`, `продажа`, `ID клиента`, `кому`, пересчитать `маржа` и `%` |
| Появился новый клиент | строка в справочнике `Клиенты` (`ID клиента` + `Клиент`) |

**Контроль консистентности (проверка `ST-02`):** у `продана` обязательно заполнены
`ID клиента`, `ДАТА ПРОДАЖИ`, `продажа`; у `доступна`/`резерв` они обязаны быть
пустыми.

## 4. Результаты аудита текущей выгрузки

**30 проверок: 26 OK, 3 WARN, 1 FAIL.**

### FAIL — закрыть до пилота

| Код | Проблема | Последствие |
|---|---|---|
| `REQS-01` | `ДАТА ПОКУПКИ` не заполнена ни у одной из 47 проданных монет | **KPI Y «закупка → продажа» на истории не считается**; невозможно оценить, насколько команда быстро оборачивает материал |

*Что сделать:* вносить дату закупки обязательно при создании строки; задним
числом проставить по документам закупки — без этого пилот не сможет закрыть
показатель Y.

### WARN — исправить по возможности

| Код | Проблема | Комментарий |
|---|---|---|
| `REQA-01` | у 10 доступных монет не заполнены `описание` (10/10), `Князь` (3/10), `ГП2` (1/10) | без `описание` система проверяет новизну только по `ГП2` и не учитывает мотив в профиле; цена и номинал восстанавливаются по аналогам |
| `DICT-03` | 4 номера ГП2 встречаются у двух разных `ID монет` (`3004`, `1575`, `1111`, `3635D` — продана и доступна) | проверить: это два разных экземпляра одного типа или дубль одной монеты |
| `FMT-01` | нет ни одной пары дат «закупка → продажа»: проверить закупка ≤ продажа невозможно | то же следствие, что и FAIL выше |

Проверки `FMT-*`, `CALC-*`, `DICT-01/02`, `ID-*`, `ST-*` прошли: UUID корректны,
статусы из справочника, маржа и % сходятся с ценами, даты в диапазоне.

## 5. Что мешает модели и как система это обходит

| Пробел | Обход в системе | Рекомендация |
|---|---|---|
| Нет цены у кандидатов | оценка по аналогам: медиана цен продажи по лестнице `ГП2 → княжество+князь → княжество → каталог`, уровень фиксируется в `цена_источник` | вносить ожидаемую цену при добавлении монеты |
| Нет `описание` у кандидатов | мотив не восстанавливается (чтобы не ломать новизну), вклад атрибута перераспределяется | заполнять мотив |
| Нет `ДАТА ПОКУПКИ` | в offline-тесте пул кандидатов строится как «не продана на момент T» | проставить даты закупок |
| Нет журнала показов/отказов | офлайн-прокси KPI (HR@5, покрытие) | ввести журнал показов рекомендаций на пилоте |

## 6. Чек-лист приёмы таблицы

- [ ] состав столбцов совпадает с фиксированным набором (`STR-01`, `STR-02`);
- [ ] нет пустых в обязательных полях (`REQ-*`, `REQS-*`);
- [ ] `СТАТУС` из справочника и согласован с реквизитами сделки (`ST-01`, `ST-02`);
- [ ] UUID и ссылки на справочник клиентов корректны (`ID-01…ID-03`);
- [ ] даты: закупка ≤ продажа, не в будущем, формат д.м.г (`FMT-01`, `FMT-02`);
- [ ] `маржа = продажа − вход`, `% = маржа / вход` (`CALC-01`, `CALC-02`);
- [ ] каталог кандидатов непуст и у каждого кандидата есть цена (`ACT-02`, `ACT-03`).

Проверка выполняется одной командой: `python -m recommender` →
`reports/data_quality_report.csv`.
